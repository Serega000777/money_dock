# Threat model

## Обязательные требования (действуют с первого коммита)

- Никаких секретов/токенов/production credentials в git (`.env` в `.gitignore`,
  `.env.example` без значений).
- Банковские пароли, PIN, CVV — не хранятся никогда; screen scraping не рассматривается
  как production-стратегия (см. ТЗ, раздел «Банковская автоматизация»).
- Refresh-токены хранятся только хэшированными (Stage 1: sha256 от случайных 256 бит).
- Bank tokens (когда появятся) — encrypted at rest.
- Все входные данные валидируются на границе API через `packages/validation` (Zod).
- Авторизация проверяется на уровне repository/service по владельцу (`user_id`) — не
  полагаемся на то, что клиент прислал "свой" ID.
- Rate limiting обязателен для auth/voice/import/export эндпоинтов (добавляется вместе с
  соответствующим модулем; `/exports` — 5/60с, см. `docs/api/README.md`).
- Login, logout, удаление операции/восстановление, экспорт и удаление аккаунта пишутся в
  `audit_logs` через единый `AuditLogService` (`apps/api/src/common/audit-log.service.ts`)
  — раздел 11 ТЗ требует трассируемости именно этих действий.
- Аудио голосовых команд удаляется после обработки, если пользователь не дал отдельного
  согласия на хранение.
- Никаких secrets в логах; логи и ошибки не содержат PII сверх необходимого — см.
  «Observability» ниже для того, что именно логируется.

## STRIDE

### Spoofing (выдать себя за другого)

| Вектор | Митигация | Статус |
| --- | --- | --- |
| Подделка Telegram `initData` | HMAC-подпись + окно свежести `auth_date` (ADR 0006) | ✅ `telegram-init-data.spec.ts` |
| Подделка access-токена | Подписан `JWT_ACCESS_SECRET` (≥32 симв., валидируется при старте), TTL 15 мин | ✅ |
| Подбор refresh-токена | 256 случайных бит, хранится только sha256-хэш | ✅ |
| Повторное использование отозванного refresh-токена | Ротация с отзывом старой сессии | ✅ `auth-and-ownership.e2e.spec.ts` |
| `POST /auth/dev-login` в проде | Жёстко `404` при `NODE_ENV=production` (`auth.service.ts`) | ✅ |
| Пользователь не видит и не может отозвать чужую активную сессию со своего устройства | — | ❌ не реализовано (спека раздел 10.2: "список активных устройств и принудительный logout") |

### Tampering (подмена данных)

| Вектор | Митигация | Статус |
| --- | --- | --- |
| Подмена тела запроса | Zod на границе API (ADR 0008) на каждом DTO | ✅ |
| Подмена суммы/баланса | Баланс всегда считается сервером из истории операций, никогда не принимается от клиента | ✅ |
| Рассинхронизация split-сумм | `assertSplitsMatchTotal` до записи в БД | ✅ `transaction.test.ts` |
| Formula injection в будущих CSV/XLSX-экспортах (`=cmd|...` в поле merchant) | `POST /exports` сейчас отдаёт только JSON — вектора нет | ⚠️ пересмотреть, если появится CSV/XLSX-экспорт |

### Repudiation (отказ от действия)

| Действие | В `audit_logs`? |
| --- | --- |
| Login / logout | ✅ |
| Удаление / восстановление транзакции | ✅ |
| Решение в Review Inbox | ✅ |
| Экспорт данных | ✅ |
| Удаление аккаунта | ⚠️ пишется, но каскадно удаляется вместе с `users` — см. «Известные ограничения» |
| Создание/изменение счёта, категории, правила категоризации | ❌ не пишется — низкая чувствительность (обратимо, не влияет на прошлые начисления), но это пробел, если понадобится полный audit trail |

### Information Disclosure (утечка данных)

| Вектор | Митигация | Статус |
| --- | --- | --- |
| IDOR на `accounts/:id`, `categories/:id`, `transactions/:id`, `notes/:id`, `insights/:id`, импорт по чужому `accountId` | Scoping по `user_id` в сервисе + e2e-тест на каждый модуль | ✅ |
| Утечка чужих данных в агрегатах (`/analytics/summary`) | Все запросы фильтруются по `user_id`; тест на изоляцию | ✅ `analytics.e2e.spec.ts` |
| Стектрейс/внутренние детали в ответе на 500 | `HttpExceptionFilter` — только `{code, message, correlationId}`, реальная ошибка только в серверном логе | ✅ |
| `CORS_ORIGIN` по умолчанию `*` | Работает в dev; **обязательно** явное значение в staging/prod | ⚠️ блокер релиза, см. ниже |
| PII/секреты в логах | HTTP access-лог (`http-access-log.middleware.ts`) пишет только method/path/status/timing/correlationId/userId — без тела, query-строки и заголовка `Authorization` | ✅ |

### Denial of Service

| Вектор | Митигация | Статус |
| --- | --- | --- |
| Брутфорс `/auth/*` | 20 запросов/60с | ✅ |
| Спам импорта | 10 запросов/60с + 5 МБ лимит на файл + месячный лимит тарифа на коммит | ✅ |
| Спам voice/text команд | 30 запросов/60с (`/commands/*`) | ✅ |
| Спам экспорта (дорогая агрегация) | 5 запросов/60с | ✅ |
| Всё остальное | Общий лимит 100 запросов/60с (`ThrottlerModule` default) | ✅ |
| Неограниченная выборка списка | `limit`/`offset` в Zod-схеме `listTransactionsQuerySchema`, `max(200)` | ✅ |
| DDoS на сетевом уровне | Ответственность деплой-инфраструктуры (CDN/WAF), не приложения | — вне зоны кода |

### Elevation of Privilege

Пока нет ролей вообще — каждый аутентифицированный пользователь имеет ровно один и тот
же набор прав (свои данные, ничего больше), поэтому повышать привилегии сейчас некуда.
Это перестанет быть верным, как только появится `AdminModule` — правило на будущее:
**ни один admin-эндпоинт не должен уйти в прод без проверки роли с первого коммита**, не
"добавим RBAC потом".

## Observability

- Каждый запрос помечается `correlationId` (`correlation-id.middleware.ts`) — эхо
  клиентского `x-correlation-id` или сгенерированный UUID, возвращается в заголовке
  ответа и в каждом error envelope.
- Каждый запрос пишет одну JSON-строку в stdout (`http-access-log.middleware.ts`):
  `{type, method, path, status, durationMs, correlationId, userId}`. Никогда — тело,
  query-строку или `Authorization`.
- Необработанные исключения логируются с полным стектрейсом и тем же `correlationId`
  (`HttpExceptionFilter`) — клиент видит только generic-сообщение, но support может найти
  точную строку лога по `correlationId` из ответа.

## Резервное копирование и восстановление (спека §33)

Автоматизированного бэкапа пока нет — ADR 0007 (никакой инфраструктуры "про запас")
здесь тоже применим: до реального продакшен-трафика это не окупает свою сложность.
Задокументированная ручная процедура на существующем `docker-compose`:

```bash
# Бэкап
docker exec money-dock-postgres-1 pg_dump -U postgres money_dock | gzip > backup-$(date +%F).sql.gz

# Восстановление в чистую БД
gunzip -c backup-2026-09-08.sql.gz | docker exec -i money-dock-postgres-1 psql -U postgres money_dock
```

Перед первым production-релизом: (1) настроить ежедневный `pg_dump` в зашифрованное
удалённое хранилище с retention 7–14 дней, (2) хотя бы один раз пройти полное
восстановление на чистом окружении и свериться с чек-листом приёмки (раздел 34 ТЗ).

## Известные ограничения

- Удаление аккаунта каскадит и его собственную запись в `audit_logs` — переживает
  удаление только структурированный серверный лог (`Logger.warn` в `UsersService`), не
  запись в БД. Если это станет проблемой для комплаенса, нужно вынести журнал удалений
  аккаунтов в таблицу без каскадной FK на `users`.
- Мягкое удаление транзакций не защищает от повторного `POST /transactions` с тем же
  `clientId`, если исходная запись уже удалена мягко — уникальный индекс
  `(user_id, client_id)` не делает исключения для `deleted_at IS NOT NULL`.
- Создание/изменение счетов, категорий и личных правил категоризации не пишется в
  `audit_logs` (см. таблицу Repudiation выше).

## Блокеры релиза (production)

1. `CORS_ORIGIN` — явное значение per-environment, никогда `*`.
2. TLS/HTTPS termination на уровне деплоя (не в коде приложения) — задокументировать в
   рантайме, которым будет обслуживаться прод.
3. Список активных устройств + принудительный logout (спека §10.2) — сейчас нет.
4. Хотя бы один реальный прогон backup → restore на чистом окружении (см. выше).
5. RBAC с первого коммита `AdminModule`, если/когда он появится — не постфактум.

Не блокеры, но стоит закрыть в ту же итерацию, что и Stage 7: audit-логи на
создание/изменение счетов и категорий, если продукту нужен полный (а не только
security-critical) audit trail.

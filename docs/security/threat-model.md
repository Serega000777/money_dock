# Threat model (черновик, полный STRIDE-разбор — Stage 7)

Полный разбор запланирован перед production (Stage 7, см.
`docs/architecture/overview.md`). Ниже — жёсткие ограничения, зафиксированные с самого
начала, чтобы к ним не пришлось возвращаться постфактум.

## Обязательные требования (действуют с первого коммита)

- Никаких секретов/токенов/production credentials в git (`.env` в `.gitignore`,
  `.env.example` без значений).
- Банковские пароли, PIN, CVV — не хранятся никогда; screen scraping не рассматривается
  как production-стратегия (см. ТЗ, раздел «Банковская автоматизация»).
- Refresh-токены хранятся только хэшированными (Stage 1: sha256 от случайных 256 бит).
- Bank tokens (когда появятся) — encrypted at rest.
- Все входные данные валидируются на границе API через `packages/validation` (Zod).
- Авторизация проверяется на уровне repository/service по владельцу (`user_id`) — не
  полагаемся на то, что клиент прислал "свой" ID.
- Rate limiting обязателен для auth/voice/import/export эндпоинтов (добавляется вместе с
  соответствующим модулем; `/exports` — 5/60с, см. `docs/api/README.md`).
- Login, logout, удаление операции/восстановление, экспорт и удаление аккаунта пишутся в
  `audit_logs` через единый `AuditLogService` (`apps/api/src/common/audit-log.service.ts`)
  — раздел 11 ТЗ требует трассируемости именно этих действий.
- Аудио голосовых команд удаляется после обработки, если пользователь не дал отдельного
  согласия на хранение.
- Никаких secrets в логах; логи и ошибки не содержат PII сверх необходимого.

## Отслеживаемые классы атак

| Класс             | Где актуально                    | Статус                                                                                                     |
| ----------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Replay            | Telegram `initData`              | ✅ Stage 1 — HMAC-подпись + окно свежести `auth_date`; тесты в `telegram-init-data.spec.ts`                |
| Token reuse       | refresh-токен                    | ✅ Stage 1 — ротация с отзывом старой сессии; тест в `auth-and-ownership.e2e.spec.ts`                      |
| IDOR              | `accounts/:id`, `categories/:id` | ✅ Stage 1 (эти модули) — scoping по `user_id` в сервисе + e2e-тест; остальные модули по мере появления    |
| Upload abuse      | импорт выписок                   | ✅ Stage 4/5 — 5 МБ на файл, 10 загрузок/60с, плюс месячный лимит тарифа на коммит                         |
| Rate limit bypass | auth                             | ✅ Stage 1 — `@nestjs/throttler`, 20 запросов/60с на `/auth/*`; voice/import/export — при появлении модуля |

## Известные ограничения (закрыть до Stage 7)

- Удаление аккаунта каскадит и его собственную запись в `audit_logs` — переживает
  удаление только структурированный серверный лог (`Logger.warn` в `UsersService`), не
  запись в БД. Если это станет проблемой для комплаенса, нужно вынести журнал удалений
  аккаунтов в таблицу без каскадной FK на `users`.
- Мягкое удаление транзакций не защищает от повторного `POST /transactions` с тем же
  `clientId`, если исходная запись уже удалена мягко — уникальный индекс
  `(user_id, client_id)` не делает исключения для `deleted_at IS NOT NULL`.

## Stage 7 (полный STRIDE + блокеры релиза)

Будет включать: auth replay, IDOR по всем модулям, upload abuse, утечку токенов,
приватность логов, rate limits, документированные бэкапы — формируется список блокеров
релиза перед production. Export/delete workflows реализованы в Stage 6 (см. выше).
